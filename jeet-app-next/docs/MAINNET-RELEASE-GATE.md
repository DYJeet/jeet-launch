```sh
node scripts/readiness/mainnet-readonly.mjs dependencies
node scripts/readiness/mainnet-readonly.mjs quote 277624 277624
node scripts/readiness/mainnet-readonly.mjs verify REVIEWED_ELF_PATH REVIEWED_SHA256 MAINNET_PROGRAM_ID UPGRADE_AUTHORITY
node scripts/readiness/mainnet-readonly.mjs verify-control MAINNET_PROGRAM_ID 0
```

Both verification commands are for read-back **after a separately approved deployment**. It derives the canonical loader PDA, checks the finalized Program owner and executable flag, pins the ProgramData authority, and compares the executable SHA-256 and padding. ## Owner identity ceremony and deployment preflight

Use the [Chromebook owner setup](CHROMEBOOK-MAINNET-IDENTITIES.md) to generate and restore the four encrypted local key files, then send only the public addresses.

Choose four distinct public signing addresses on owner-controlled devices for the new program, containment authority, deployment payer, and initial loader upgrade authority. The existing approved treasury is a fifth, fixed role. The long-term upgrade authority may be transferred to a reviewed multisig after its controls are exercised off Mainnet and the exact transfer is separately approved. A simple recent blockhash, a funded address, or a CLI configuration does not prove control.

Generate private keys only on owner-controlled hardware or an offline owner device. Store backups there. Send only public addresses and the detached signatures. Sign the exact role-specific text in `challenge.json` with the corresponding owner-controlled signer using Solana off-chain message format v1 with that role's address as the sole required signatory, or raw Ed25519 signing of the displayed UTF-8 text. Omit a trailing newline. Use a trusted local signer already compatible with one of these formats. The JSON signature map accepts the detached 64-byte signatures as base58 strings under `program`, `containmentAuthority`, `deploymentPayer`, `initialUpgradeAuthority`, and `treasury`. Keep the same challenge for all five roles. It expires 24 hours after issuance and is bound to the selected source commit and public identities. Treat proof as confirmation of key control at signing time. It authorizes no transaction.

```sh
node scripts/readiness/mainnet-identities.mjs issue SOURCE_COMMIT PROGRAM CONTAINMENT PAYER INITIAL_UPGRADE > challenge.json
node scripts/readiness/mainnet-identities.mjs verify SOURCE_COMMIT challenge.json signatures.json
node scripts/readiness/mainnet-readonly.mjs preflight SOURCE_COMMIT challenge.json signatures.json ELF_PATH SHA256 PROGRAMDATA_CAPACITY
```

Keep ceremony files outside the build checkout. The preflight expects the builder-generated `build-manifest.json` alongside the executable. It rejects occupied program or ProgramData accounts, unexpected control or wallet accounts, and changed Raydium terms. Its rent status does not cover network fees. Before any spending, price the precise unsigned loader message list and separate control initialization, confirm balance headroom, and agree the maximum debit. Keep the clean build and independent review evidence with the approval. The local replay and dependency poll are complementary to the review of the final binary, signer ceremony, and upgrade rollback.

## Owner-controlled release procedure

1. Choose a new Mainnet program identity and a separate owner-controlled fee payer. Keep deployment signing on an owner-controlled device. Keep the upgrade authority in an owner-approved hardware-backed or reviewed multisig workflow. Verify its authority-transfer and upgrade capability off Mainnet first. Keep the existing treasury. Prove control with a clearly scoped, non-transaction challenge before approving any treasury funding or claim.
2. Compile the dedicated Mainnet profile from a clean source checkout with [the reproducibility script](../scripts/readiness/build-mainnet-candidate.sh). Supply separate owner-controlled `JEET_MAINNET_PROGRAM_ID` and `JEET_MAINNET_CONTAINMENT_AUTHORITY` public inputs. Restrict the exposed opcodes to the reviewed release surface. Pin the crate lock, Solana/Agave SBF tools and Raydium binary/config. Start with the retained Devnet reproduction inputs (SBF v0 and platform tools v1.57), verify their suitability, and produce two clean builds from the exact Mainnet identity and source commit. Compare SHA-256 hashes and record ELF capacity, tool versions, and dependency hashes. The prior Devnet build and toolchain evidence stay available for comparison.
3. Provision a separate HTTPS index service on a dedicated persistent volume using `JEET_SHARED_MAINNET_PROGRAM_ID`, a new server credential, and a separate database path. The Node service binds the file to the full Mainnet genesis and program and rejects reuse of an existing Devnet database. Restore a backup off production and check event/checkpoint integrity. Use separate frontend wallet, RPC, metadata, and auth configuration. The read-only Mainnet probe uses the public RPC; configure rate limits, RPC health, metadata limits and persistence for the actual launch service.
4. Review exact unsigned create, trade, claim and migration messages for the built candidate. Run a focused local replay on the pinned public dependency bytes and do one owner-approved Devnet signing test. Mainnet JeeT simulation against an undeployed program cannot validate custody or ceremony success. If a later real deployment is approved, perform finalized read-back and restricted unsigned Mainnet simulation before authorizing any trade or admitting users.
5. Initialize release control at mode 0 (closed). Verify read-back. Request separate approval for mode 1 (authority-only pilot) and later mode 2 (public). Start with a private, authority-only launch window and reviewed spend limits. Keep the existing read-only public deployment as rollback. If an invariant, authority, dependency hash, or RPC health check changes, disable gated site writes and forwarding immediately, coordinate approved on-chain closure to mode 0, keep sells and earned claims available where safe, preserve logs/receipts and inspect finalized accounts. A frontend rollback cannot undo chain transactions or stop direct program calls. Any on-chain restriction or binary rollback requires reviewed authority action and separate authorization.
